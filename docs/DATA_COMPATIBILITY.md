# Data Compatibility & Migration Policy

> **Purpose:** Ensure that any future release of IYPM (including the planned Smart TV companion app) never causes data loss for existing users, regardless of upgrade timing or device mix.

---

## Core Principles

1. **Additive Only** — New fields, keys, tables, and stores may be added. Existing ones are never renamed or removed without a deprecation window.
2. **Forward-Compatible Reads** — New code must tolerate data written by old code (missing fields → sensible defaults via normalizers).
3. **Mixed-version writes are not automatically compatible** — Older clients may ignore or overwrite unknown fields. Test each supported client pair explicitly, or stop the older client from writing after migration.
4. **No silent data loss** — Extension/schema migrations and background sync never wipe user data. A user-selected overwrite restore remains an explicit destructive action with a clear warning; merge is the default recovery path.
5. **Version support is an explicit matrix** — Do not claim mixed-version sync unless that exact client/backend pair is covered by a migration or interoperability test. Unsupported combinations must stop before data writes.

## Storage Layers & Rules

### 1. IndexedDB (`yph_metadata_db_v2`, store: `metadata`)

- **Current stores:** `yph_metadata_db_v2` (IndexedDB version 1, object store `metadata`) and `yph_sync_shadow_v1` (version 1, object store `shadow`). These are separate databases with independent version counters.
- `db-service-core.ts` currently creates `metadata` when absent; it does not yet have a general migration registry. A version bump must add explicit, idempotent upgrade steps in `onupgradeneeded`.
- **Rule:** Upgrade steps are additive. Never delete an existing store or clear records as part of extension startup. Preserve old data until a new representation has been written and verified.
- **Normalizers** (`normalizeVideoMeta`) supply defaults for older metadata records; test this against fixtures from the last released version.

- **Rule:** Never rename or remove a data key without an idempotent migration and a compatibility window. Keep credentials/status/cursors out of portable backups and user-preference sync.

### 3. Backup Format (`schemaVersion`)

- Current: `CURRENT_BACKUP_SCHEMA_VERSION = 2` in `backup-format.ts`.
- **Accept:** legacy playlist-array exports and object schema versions 1 and 2. Schema v1 migrates in memory to v2 through `migrateV1ToV2`; schema v2 is the current shape.
- **Reject:** non-integer/invalid versions, unsupported future versions, malformed payloads, and any older version without a complete migration chain. Validate and migrate before any local mutation.
- Export/import settings use `selectSyncableSettings()` as an allowlist, excluding sync keys, endpoint credentials, status, cursors, and unknown storage keys.

**Version-bump acceptance:** Keep `CURRENT_BACKUP_SCHEMA_VERSION` as the sole current-version constant. Before a bump, implement every sequential migration from every still-supported version to the new version; keep migration pure (in-memory only) and do not rewrite the source backup.

- Add released-version JSON fixtures for each accepted version and test both `merge` and `overwrite` import, including thumbnails, metadata, history, preferences, and unknown-but-preserved data fields.
- Test the new-version export shape, round-trip import, and migration invariants: all user payload survives, defaults are supplied only for fields absent in old versions, and secret/internal settings remain excluded by the allowlist.
- Test malformed/non-integer/unsupported future versions and assert validation returns before any local, IndexedDB, thumbnail, playlist, history, or settings write. Test that a current-version backup is not mutated by migration.
- Update `CompleteBackupFile`, the migration registry, `docs/DATA_COMPATIBILITY.md`, and changelog in the same change; run the focused backup tests plus `npm run check` and `npm run build` on the exact feature head.

### 4. Sync Wire Formats

- The snapshot envelope codec (`snapshot-codec.ts`) is legacy and uses `schemaVersion = 1`; it rejects versions it does not understand. Do not treat that version as the current relay format.
- The active v2 relay uses per-record envelopes (`record-codec.ts`, `RECORD_VERSION = 2`) and HKDF-derived keys, while the released v1 path used a single encrypted snapshot and PBKDF2-derived keys. These formats and key derivations are not wire-compatible.
- Any future record or snapshot version must have an explicit reader/migration path and fixtures from the prior shipped version. Unknown formats fail before apply and stay retryable; never silently initialize a new remote space as a substitute for legacy data.
- Nearby sessions negotiate their own protocol version and only exchange record versions both peers support.

### 5. Supabase / Hosted Relay

- Schema and wire versions are independent. The v2 relay uses `sync_spaces` and `sync_records`; direct anon table reads returning 401 are expected because access is RPC-only.
- A read-only probe on 2026-11-04 returned HTTP 404 for `relay_snapshots`, the v1 single-snapshot table. This proves the old table is currently unavailable, but does not reveal whether it contained user rows or whether a Supabase backup can restore them.
- **Release gate:** Do not claim existing v1 relay users are migrated or data-safe until an owner verifies whether a recoverable hosted backup exists and decides the recovery/announcement path. Application code must not silently claim an empty v2 space for a detected legacy client.
- Future hosted schema changes use additive, numbered migrations and retain the prior protocol for the announced compatibility window. Never drop an old table or endpoint until migration evidence and the supported-client window are closed.

## Checklist for Any Future Release

Before merging a PR that touches storage or sync:

- [ ] No storage keys renamed or removed without idempotent migration
- [ ] No IndexedDB stores dropped without tested migration
- [ ] New fields have defaults in normalizers
- [ ] Backup export/import use the settings allowlist and never serialize sync credentials
- [ ] Every supported backup version has a tested migration path; unknown versions reject before writes
- [ ] Record, session, and relay protocol versions are tracked independently
- [ ] Legacy relay data is preserved/migrated or a documented recovery blocker prevents silent v2 setup
- [ ] Hosted SQL migration state is read back; a local SQL pass is not hosted evidence
- [ ] Old backup fixtures import; mixed-version sync is claimed only for tested pairs
- [ ] Nearby test proves no external signaling/STUN/TURN/relay traffic and real-device acceptance is recorded separately

## What Breaks Users (and how to avoid it)

| Mistake                                           | Consequence                              | Prevention                                                         |
| ------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------ |
| Renaming a storage key                            | Old data invisible to new code           | Add new key, keep reading old                                      |
| Dropping an IndexedDB store                       | Total metadata cache loss                | Migrate in `onupgradeneeded`                                       |
| Accepting an old version with no transform        | Silent shape corruption or skipped data  | Require an explicit migration step for every supported version     |
| Requiring a new field without default             | Old records fail normalization           | Always default in normalizer                                       |
| Changing Supabase column type                     | Old clients get type errors              | Add a new column; deprecate only after the client window closes    |
| Bumping backup version without migration          | Old backups rejected or misread          | Add and test a sequential migration before accepting that version  |
| Dropping the v1 relay before recovery is verified | Remote-only snapshots become unavailable | Preserve/recover the old source or block v2 rollout and warn users |

## Smart TV App Considerations

The planned TV companion app is a **read-only consumer** of the same Supabase data. It must:

- Use the same table schemas (no TV-specific columns in shared tables).
- Store device-pairing state in **new tables only** (`device_codes`, `paired_devices`).
- Never write to playlist/metadata tables — only read.
- Accept that desktop clients may write fields the TV app doesn't know about (ignore unknown fields).

This ensures the TV app can be developed and released independently without risking desktop user data.
